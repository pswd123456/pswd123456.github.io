这是 Ragas 源码解读的第四部分：**生产环境稳定性 (Production Readiness)**。

在 Demo 阶段，我们通常只跑几条数据，一切都很美好。但当你试图在生产环境中评估上千条数据，或者使用不稳定的 LLM 服务时，噩梦就开始了：**超时 (Timeout)**、**速率限制 (Rate Limit)**、**网络抖动**。

这部分源码解读主要关注 `ragas/run_config.py`，它是控制这些行为的总开关。

---

## 1. 全局控制中心：`RunConfig`

`RunConfig` 是一个简单的数据类（Dataclass），但它决定了 Ragas 评估任务的“韧性”。

```Python
# 位于 ragas/run_config.py

@dataclass
class RunConfig:
    """
    Configuration for a timeouts, retries and seed for Ragas operations.
    """
    timeout: int = 180          # 单次 LLM 请求的最大等待秒数 (默认 3分钟)
    max_retries: int = 10       # 失败后的最大重试次数 (默认 10次)
    max_wait: int = 60          # 重试之间的最大等待间隔 (默认 60秒)
    max_workers: int = 16       # 并发线程数 (默认 16)
    exception_types: t.Union[
        t.Type[BaseException],
        t.Tuple[t.Type[BaseException], ...],
    ] = (Exception,)            # 哪些异常触发重试 (默认所有 Exception)
    log_tenacity: bool = False  # 是否打印重试日志
    seed: int = 42              # 随机种子
```

**源码解读与使用建议：**

1. **`timeout` (超时)**：这是最容易“暴雷”的参数。默认 180秒对于简单的 GPT-3.5 够用了，但对于复杂的 **GPT-4** 推理，或者是响应较慢的 **本地模型**，180秒经常不够，导致 `asyncio.TimeoutError`。
    
    - **建议**：如果你的评估经常跑挂，第一件事就是把这个值设大，比如 `RunConfig(timeout=600)`。
        
2. **`max_workers` (并发)**：Ragas 默认开 16 个并发。
    
    - **痛点**：如果你用的是免费版 API 或者 TPM (Tokens Per Minute) 限制很严格的账号，16 并发会瞬间打爆你的 Rate Limit。
        
    - **建议**：如果遇到 `RateLimitError`，请把 `max_workers` 调小，甚至设为 1（串行执行）。
        
3. **`exception_types` (重试触发条件)**：默认情况下，Ragas 遇到**任何** `Exception` 都会重试。
    
    - **细节**：这包括了网络错误、解析错误等。配合 `max_retries=10`，Ragas 实际上非常“顽固”，会尽最大努力拿到结果。

## 2. 重试机制的实现：`add_async_retry`

Ragas 并没有自己造轮子，而是使用了 Python 生态中著名的 `tenacity` 库来实现重试。

```Python
# 位于 ragas/run_config.py

def add_async_retry(fn: WrappedFn, run_config: RunConfig) -> WrappedFn:
    """
    Decorator for retrying a function if it fails.
    """
    # 如果开启了日志，会配置 tenacity 的 logger
    if run_config.log_tenacity is not None:
        logger = logging.getLogger(f"TENACITYRetry[{fn.__name__}]")
        tenacity_logger = after_log(logger, logging.DEBUG)
    else:
        tenacity_logger = after_nothing

    r = AsyncRetrying(
        wait=wait_random_exponential(multiplier=1, max=run_config.max_wait), # 指数退避策略
        stop=stop_after_attempt(run_config.max_retries),      # 最大尝试次数
        retry=retry_if_exception_type(run_config.exception_types), # 捕获哪些异常
        reraise=True,
        after=tenacity_logger,
    )
    return r.wraps(fn)
```

**源码解读**：

- **指数退避 (Exponential Backoff)**：`wait_random_exponential` 意味着每次重试的等待时间会指数级增加（1s, 2s, 4s...），直到达到 `max_wait` (60s)。这对缓解 API 的拥堵非常有帮助。
    
- **装饰器模式**：这个函数通常包裹在 LLM 的 `agenerate_text` 方法外面（我们在 `llms/base.py` 中见过它）。

## 3. 实战：如何应用自定义配置

了解了源码后，正确的使用姿势是在调用 `evaluate` 时传入自定义的 `RunConfig`。

```Python
from ragas import evaluate, RunConfig
from ragas.metrics import faithfulness, answer_relevancy

# 场景：我的模型很慢，且 API 限制很严（每分钟只能调 2 次）
my_config = RunConfig(
    timeout=600,        # 给模型 10 分钟时间思考
    max_retries=5,      # 失败重试 5 次
    max_wait=120,       # 重试间隔最大 2 分钟
    max_workers=2       # 降低并发，避免被封号
)

results = evaluate(
    dataset=my_dataset,
    metrics=[faithfulness, answer_relevancy],
    run_config=my_config  # <--- 注入配置
)
```

在 BaseRagasLLM 中的生效流程：

当你把 my_config 传给 evaluate 后：

1. `evaluate` 函数接收 `run_config`。
    
2. `evaluate` 遍历所有 metrics，调用 `metric.init(run_config)`。
    
3. `metric.init` 内部调用 `self.llm.set_run_config(run_config)`。
    
4. LLM 在执行 `generate` 时，会通过 `add_async_retry` 装饰器应用这些重试参数。
    

## 总结：第四部分核心知识点

1. **超时是头号杀手**：如果你遇到 `asyncio.TimeoutError`，不要怀疑网络，先改 `RunConfig(timeout=...)`。
    
2. **并发控制速率**：通过 `RunConfig(max_workers=...)` 来适配你的 API Rate Limit。
    
3. **重试机制**：Ragas 使用 `tenacity` 进行指数退避重试，默认重试 10 次，这保证了在不稳定的网络下依然能跑完评估。
    
4. **配置注入**：通过 `evaluate(run_config=...)` 一键全局生效，不需要去改每个 Metric 的代码。

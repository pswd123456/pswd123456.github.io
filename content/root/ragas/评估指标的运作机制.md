这是 Ragas 源码解读的第二部分：**评估指标的运作机制**。

在第一阶段，我们了解了数据如何“进”到 Ragas。现在我们要深入“黑盒”内部，看看指标（Metrics）到底是如何工作的。这部分主要涉及 `ragas/metrics/base.py`，它是所有指标的基石。

理解这部分源码，能帮你解决以下常见问题：

- **“为什么报错说缺列 (`ValueError: ... required columns`)？”**
    
- **“为什么我的指标跑出来全是 0 或 NaN？”**
    
- **“如何自定义一个简单的指标？”**

---

## 1. 指标的契约：`Metric` 基类

所有的指标（如 Faithfulness, AnswerRelevancy）都继承自 `Metric` 类。这个类规定了“在这个指标能工作之前，必须满足什么条件”。

### 核心属性：`required_columns`

这是调试报错时最重要的属性。

```Python

# 位于 ragas/metrics/base.py

@dataclass
class Metric(ABC):
    # ...
    _required_columns: t.Dict[MetricType, t.Set[str]] = field(default_factory=dict)

    @property
    def required_columns(self) -> t.Dict[str, t.Set[str]]:
        # ... (逻辑省略)
        # 返回类似: {'single_turn': {'user_input', 'response', 'retrieved_contexts'}}
        return required_columns
```

**源码解读与使用建议：**

- **硬性约束**：每个指标内部都定义了它需要哪些列。例如 `Faithfulness` 通常需要 `question` (user_input), `answer` (response), 和 `contexts` (retrieved_contexts)。
    
- **报错根源**：第一阶段提到的 `validate_required_columns` 函数，就是读取这个属性。如果你的数据集里只有 `question` 和 `answer`，但你跑了 `Faithfulness`（它需要 `contexts`），程序就会在这里抛出异常。
    
- **调试技巧**：如果你不知道某个指标需要什么列，可以直接打印它：`print(my_metric.required_columns)`。

## 2. 动力的来源：`MetricWithLLM`

绝大多数 Ragas 指标（如 `Faithfulness`, `AnswerRelevancy`）都需要 LLM 来进行判断。它们都继承自 `MetricWithLLM`。

```Python

# 位于 ragas/metrics/base.py

@dataclass
class MetricWithLLM(Metric, PromptMixin):
    llm: t.Optional[BaseRagasLLM] = None
    
    def init(self, run_config: RunConfig) -> None:
        if self.llm is None:
            raise ValueError(
                f"Metric '{self.name}' has no valid LLM provided..."
            )
        # 将全局的 run_config (包含超时、重试设置) 注入到 LLM 中
        if isinstance(self.llm, BaseRagasLLM):
            self.llm.set_run_config(run_config)
```

**源码解读与使用建议：**

- **LLM 注入时机**：还记得第一阶段 evaluate 函数 *([[核心入口与数据契约#2. 执行入口：`ragas/evaluation.py`]])* 里的逻辑吗？它会把全局的 `llm` 塞给这里。但如果你在初始化指标时就指定了 `Metric(llm=my_custom_llm)`，那么它就会用你指定的这个，而忽略全局的。

```python
def _build_metrics(self, ragas_llm, ragas_embed):

        metric_builders = {

            "faithfulness": lambda: Faithfulness(llm=ragas_llm),

            "answer_relevancy": lambda: AnswerRelevancy(llm=ragas_llm, embeddings=ragas_embed),

            "context_recall": lambda: ContextRecall(llm=ragas_llm),

            "context_precision": lambda: ContextPrecision(llm=ragas_llm),

            "context_entities_recall": lambda: ContextEntityRecall(llm=ragas_llm),

            "answer_accuracy": lambda: AnswerAccuracy(llm=ragas_llm)

        }
```

- **PromptMixin**：这个类让指标拥有了管理 Prompt 的能力。如果你觉得 Ragas 默认的 Prompt 不好（比如在中文场景下），你可以通过访问指标的 `prompt` 属性来修改它（通常涉及 `adapt` 或 `set_prompt` 方法，虽然不在 base.py 中，但源于此继承关系）。

```python
adapted_prompts = await metric.adapt_prompts(language=language, llm=metric.llm)
```

## 3. 执行的分野：`SingleTurnMetric` vs `MultiTurnMetric`

Ragas 2.0 明确区分了**单轮**和**多轮**指标。这是为了解决旧版本中混用导致的逻辑混乱。

### `SingleTurnMetric` (单轮指标)

这是最常用的类型。

```Python
# 位于 ragas/metrics/base.py

class SingleTurnMetric(Metric):
    def _only_required_columns_single_turn(self, sample: SingleTurnSample) -> SingleTurnSample:
        # 只提取该指标需要的字段，减少传输给 LLM 的数据量（如果指标内部逻辑不当的话）
        # ...
        return SingleTurnSample(**sample.model_dump(include=required_columns))

    async def single_turn_ascore(self, sample: SingleTurnSample, ...) -> float:
        # ...
        # 1. 过滤数据
        sample = self._only_required_columns_single_turn(sample)
        # 2. 开启一个新的回调分组 (Trace Group)
        rm, group_cm = new_group(self.name, ...)
        
        # 3. 调用具体的打分逻辑 _single_turn_ascore (由子类实现)
        score = await asyncio.wait_for(
            self._single_turn_ascore(sample=sample, callbacks=group_cm),
            timeout=timeout,
        )
        return score
```

**源码解读与使用建议：**

- **抽象方法 `_single_turn_ascore`**：所有的具体指标（如 `Faithfulness`）只需要实现这个方法。它们接收一个标准的 `SingleTurnSample` 对象，返回一个 `float` 分数。
    
- **异步优先**：Ragas 核心全是 `async` 的。如果你自定义指标，最好也实现 `_ascore` 而不是同步的 `score`，否则会阻塞整个评估流程，导致极慢。
    
- **超时控制**：注意 `asyncio.wait_for(..., timeout=timeout)`。这个 `timeout` 来自 `RunConfig`。如果你的 LLM 很慢，经常报 TimeoutError，就是这里触发的。
    

### `MultiTurnMetric` (多轮指标)

```Python
# 位于 ragas/metrics/base.py

class MultiTurnMetric(Metric):
    # 结构与 SingleTurnMetric 几乎一致
    async def multi_turn_ascore(self, sample: MultiTurnSample, ...) -> float:
        # ...
```

*注: multiTurnMetric用来处理带有历史的多轮对话*

|**特性**|**SingleTurn (单轮)**|**MultiTurn (多轮)**|
|---|---|---|
|**场景**|传统的 RAG 问答，像搜索引擎|Agent 代理、聊天机器人|
|**User Input**|`str` (一句话)|`List[Message]` (对话历史)|
|**Context**|仅针对当前问题的检索结果|可能包含每轮对话的中间检索结果|
|**评估重点**|准确性、幻觉、相关性|逻辑连贯性、工具使用、任务完成度|
|**对应基类**|`SingleTurnMetric`|`MultiTurnMetric`|

**使用注意**：不要把单轮数据喂给多轮指标，反之亦然。虽然 `evaluate` 会帮你做检查，但在自定义 pipeline 时要格外注意。

## 4. 简单指标的捷径：`SimpleBaseMetric`

如果你想写一个不依赖复杂逻辑的指标（比如简单的正则匹配，或者判断回复长度），可以看这个类。

```Python
# 位于 ragas/metrics/base.py

@dataclass
class SimpleBaseMetric(ABC):
    # 定义了 allowed_values (比如 ["pass", "fail"] 或 (0, 1))
    allowed_values: AllowedValuesType = field(default_factory=lambda: ["pass", "fail"])
    
    # 提供了 batch_score 的默认实现
    def batch_score(self, inputs: t.List[t.Dict[str, t.Any]]) -> t.List["MetricResult"]:
        return [self.score(**input_dict) for input_dict in inputs]
```

**源码解读**：

- **简化开发**：继承这个类，你只需要实现 `score` 方法，Ragas 会自动帮你处理批量化（虽然是简单的循环调用）。
    
- **输出结构化**：它强制返回 `MetricResult`，这比单纯返回 float 更丰富，可以包含 `reason`（理由）。

---

## 总结：第二部分核心知识点

1. **查缺补漏**：遇到 `ValueError` 说缺列时，检查该指标的 `required_columns` 属性。
    
2. **LLM 依赖**：继承自 `MetricWithLLM` 的指标必须有 LLM 才能跑。`evaluate` 会自动注入，但你也可以手动指定。
    
3. **单/多轮分离**：清楚你的业务场景是 Single Turn 还是 Multi Turn，选错指标类型（基类）会导致无法计算。
    
4. **异步核心**：核心执行逻辑在 `_single_turn_ascore` 中。自定义指标时，尽量写异步代码以利用 Ragas 的并发能力。
    
5. **超时处理**：打分过程中的 Timeout 是在 `SingleTurnMetric.single_turn_ascore` 这一层被捕获和控制的，调整 `RunConfig` 可以解决。

基于 `LightRAG` 代码库（特别是 `lightrag.py` 和 `operate.py`），检索流程（Retrieval Process）是一个高度模块化且分阶段的过程。核心逻辑主要由 `LightRAG.query` (或 `aquery`) 触发，并根据设定的 `mode`（查询模式）分流到不同的处理函数中。

以下是 LightRAG 检索流程的详细解析：

## 1. 入口与模式分流

用户调用 `lightrag.py` 中的 `query()` 或 `aquery()` 方法时，首先会根据 `QueryParam` 中的 `mode` 参数决定检索策略。

主要的几种模式如下：

- **`naive`**: 传统的 RAG 模式，仅进行向量检索。
    
- **`local`**: 侧重于局部细节，利用知识图谱中的实体（Entities）进行检索。
    
- **`global`**: 侧重于全局概览，利用知识图谱中的关系（Relationships）进行检索。
    
- **`hybrid`**: 结合 `local` 和 `global`。
    
- **`mix`**: 结合知识图谱（`hybrid`）和向量检索（`naive`）。

---

## 2. 检索流程详解

我们将流程分为 **关键词提取**、**上下文构建（检索核心）** 和 **答案生成** 三个阶段。

### 第一阶段：查询理解与关键词提取 (Keyword Extraction)

适用模式: local, global, hybrid, mix

(注意：naive 模式跳过此步)

在 `operate.py` 的 `kg_query` 函数中：

1. **提取关键词**: 系统调用 `get_keywords_from_query` -> `extract_keywords_only`。
    
2. **LLM 介入**: 使用 LLM 分析用户 Query，提取出两类关键词：
    
    - **High-level keywords (高层关键词)**: 用于全局检索 (Global retrieval)。
        
    - **Low-level keywords (低层关键词)**: 用于局部检索 (Local retrieval)。
        
3. **缓存机制**: 提取结果会被缓存，避免重复消耗 LLM Token。
    

### 第二阶段：上下文构建 (Context Building)

这是检索的核心，主要发生在 `operate.py` 的 `_build_query_context` 函数中，它包含四个子步骤：

2.1 执行搜索 (_perform_kg_search)

根据模式不同，搜索源不同：

- **Naive 模式** (`naive_query` -> `_get_vector_context`):
    
    - 直接在 `chunks_vdb`（文本块向量库）中搜索与 Query 相似的文本块。
        
- **Local 模式**:
    
    - 使用 **Low-level keywords** 在 `entities_vdb` 中搜索相似实体。
        
    - 通过 `_get_node_data` 获取关联的节点（实体）及其一度邻居。
        
- **Global 模式**:
    
    - 使用 **High-level keywords** 在 `relationships_vdb` 中搜索相似关系。
        
    - 通过 `_get_edge_data` 获取关联的边（关系）及其连接的实体。
        
- **Mix 模式**:
    
    - 同时执行 Local 和 Global 的图搜索。
        
    - 额外执行类似 Naive 模式的向量搜索 (`_get_vector_context`) 来补充文本块上下文。
        

**2.2 Token 截断 (`_apply_token_truncation`)**

- 搜索到的实体和关系可能非常多。系统会根据 `max_entity_tokens` 和 `max_relation_tokens` 配置，对检索到的实体和关系列表进行截断，保留相关性最高的条目。
    

**2.3 文本块映射与合并 (`_merge_all_chunks`)**

- 系统不仅返回实体和关系，还会找回包含这些信息的**原始文本块 (Chunks)**。
    
- **实体关联块**: 通过 `_find_related_text_unit_from_entities` 找回支撑实体的原始文本。
    
- **关系关联块**: 通过 `_find_related_text_unit_from_relations` 找回支撑关系的原始文本。
    
- **向量关联块**: Mix 模式下包含直接向量检索到的块。
    
- **合并**: 将上述来源的 Chunks 进行合并和去重。
    

**2.4 构建提示词上下文 (`_build_context_str`)**

- 将筛选后的**实体 (Entities)**、**关系 (Relations)** 和 **文本块 (Chunks)** 格式化为 JSON 字符串或列表。
    
- 生成引用列表 (`Reference List`)，对应原始文件路径。
    
- 这些内容被填入 Prompt 模板（`PROMPTS["kg_query_context"]` 或 `PROMPTS["naive_query_context"]`）。
    

### 第三阶段：答案生成 (LLM Generation)

**函数**: `operate.py` 中的 `kg_query` 或 `naive_query`

1. **组装系统提示词**: 将构建好的 Context 填入系统提示词模板（`PROMPTS["rag_response"]`）。
    
2. **缓存检查**: 计算参数哈希，检查是否有相同的查询缓存。
    
3. **调用 LLM**:
    
    - 如果缓存未命中，调用 `global_config["llm_model_func"]`。
        
    - 传入用户 Query 和带有丰富上下文的 System Prompt。
        
4. **流式/非流式返回**: 根据 `stream` 参数决定返回字符串还是迭代器。

---

## 总结：数据流向图

1. User Query
    

    ↓

    
2. Keyword Extraction (LLM: Query -> Keywords)
    

    ↓

    
3. **Vector Search** (Keywords -> VDBs)
    
    - Local: Keywords -> Entities VDB
        
    - Global: Keywords -> Relationships VDB
        
    - Naive/Mix: Query -> Chunks VDB
        

        ↓

        
4. **Graph Traversal** (VDB Results -> Graph Storage)
    
    - 获取完整的节点(Node)和边(Edge)属性。
        

        ↓

        
5. **Chunk Retrieval** (Graph Elements -> Text Chunks Storage)
    
    - 反查支撑这些图元素的原始文本块。
        

        ↓

        
6. **Context Construction** (Filters & Formatting)
    
    - Entities + Relations + Chunks -> Context String
        

        ↓

        
7. **Final Generation** (LLM: Query + Context -> Answer)
    

这个流程的设计关键在于 `operate.py` 实现了将非结构化的文本块检索与结构化的知识图谱检索（实体/关系）相结合，通过多路召回（Graph + Vector）来增强上下文的丰富性和准确性。

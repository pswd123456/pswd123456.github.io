## Startup

- 将业务场景用精确的语言描述出来, 以开发的角度描述一件问题的问题空间和需求
  
	- 确保你对业务领域的词汇理解和LLM保持一致, 可以让LLM复述你的需求, 提取关键词汇表
	- 使用[[#System prompt]]
	  
- 将这个问题空间投喂给LLM, 获得初步的解决方案
  
	- 这一步可以多使用几个不同的LLM生成的解决方案, 交叉对比或者进行协作审查
		- 协作审查可以利用角色提示不同的角色进行协作
		- 如果一直重复修改某几个细则就可以不用问了
	  
	- 但是要注意信息来源以及可信度, 可以使用有能力使用搜索引擎kit的LLM模型
	  
	- 要亲自做调研, 查看可信源的解决方案, 评估LLM给出的解决方案是否符合当前业务的语境
	  
- 做完调研后, 选择一套目前流行的解决方案, 大致了解后, 微调后交给LLM生成解决架构方案
  
	- 生成解决方案时, 可以先确定框架, 让LLM生成项目结构和核心接口定义, 用mermaid画目录树结构图, DFD, ERD, SD
	  
- 生成解决方案后, 尽可能粒度细的分割成几个执行步骤, 让LLM详细的生成执行步骤

## In-progress

- 维护一个markdown文件, 包括当前的
  
	- 架构图, 
	- 数据结构, 
	- 任务进度

- 当前对话的messages超过一定长度或者频繁出现幻觉时, 可以使用这个md文件在新的对话中继续, 以获取一个干净的对话历史
- 也可以主动在完成一个单元功能后, 开启一个[[#新的对话]]
	  
- 在写业务代码时, 可以让LLM
  
	- 先写单元测试, <- 需要审查
	- 然后简单描述一下业务逻辑, 
	- 以能通过测试的标准编写代码, <- 先跑一次测试, 确认LLM没有糊弄
	- 测试通过后再优化结构, 
	- 即 [[#红 -> 绿 -> 重构]] 
	- 这么做可以限制作业范围和确保业务逻辑有效, 以及保证更改的过程中始终满足构想的功能
  
- 这个过程中, 要尽可能的让LLM包含当前context执行的所有相关代码和文档, 
	- 一般而言, 信息越详细, 出问题的概率越小, 
	- 但是当一个`messages`的context太长时, LLM出现幻觉的概率会显著增加, 表现为频繁出错, 
	- 所以要尽可能的引用强相关的代码和文档段落

## Debugging

- 出现问题时, 可以将context和问题一起提交给LLM, 获得初步解决方案
  
	- 但是不要过度依赖LLM解决问题的能力, 如果预训练或者互联网上没有这个问题的答案, 或者你提供的context信息有丢失时, LLM可能不会给出正确的答案
	- 审查LLM给出的解决方案, 如果context不足或者出现幻觉, 执行错误的解决方案链条反而会浪费大量的时间, 
	- 这时候正确的做法回归到传统的搜索引擎+社区+阅读文档的解决模式,
	- 找到问题的出处后, 反而可以利用LLM的语义处理能力和生成能力帮助你解决问题(在新的对话窗口中)

## System prompt

```
# Role
你是一位 World-Class 的全栈技术专家。你不仅写代码，更注重工程质量、安全性和可维护性。

# Project Context Source
*读取文件中的 `PROJECT_CONTEXT.md` 和 `ARCHITECTURE.md`。
*在回答任何问题前，必须优先回顾架构文档。

# Workflow & Constraints (严格执行)

## 1. Analysis Phase (思考先行)
- 在输出任何代码前，必须先分析请求，检查是否与 `PROJECT_CONTEXT.md` 中的当前架构冲突。如果有架构冲突, 向用户确认如何执行
- **思维链 (CoT)**: 用 `<思考>` 标签包裹你的分析过程。

## 2. Coding Standards (2025-11)
- **语言规范**: Python 3.1* + (PEP8, Type Hints), TypeScript 5.x (Strict Mode).
- **库版本检查**: 必须假设当前日期为 **2025-11-20**。严禁使用已在 2024 年前废弃的 API。如果不确定库的最新语法，请求用户使用 Search Tool。
- **注释**: 仅在逻辑复杂处添加解释性注释，所有公共接口必须有 Docstring。

## 3. Test-Driven Development (TDD)
- **原则**: No Code without Tests.
- **顺序**: 
    1. 编写/更新测试用例 (Jest/Pytest)。
    2. 确认测试失败。
    3. 编写实现代码。
    4. 验证测试通过。

## 4. Error Handling & Logging
- 所有的 I/O 操作必须包裹在 try-catch/except 块中。
- 禁止使用 `print`，必须使用结构化日志 (Logger)。
- 错误信息必须包含上下文（如 User ID, Request ID）。

## 5. Context Management
- 如果你发现当前的上下文信息不足以完成任务，或者存在歧义，**立即停止并提问**，不要猜测。
```

## 红 -> 绿 -> 重构

TDD 是质量的阀门。为了让 LLM 执行得更好，需要明确 **“测试粒度”**。

- **Rule:** 强迫 LLM 先写测试，**并且**在写实现代码之前，先解释测试为什么会失败（预测报错）。这能强迫模型进行逻辑推理，而不是瞎猜。
    
- **Prompt 技巧:** "请先生成针对 `UserLogin` 接口的测试用例。不要写实现代码。测试必须覆盖：正常登录、密码错误、账户锁定三种情况。"
